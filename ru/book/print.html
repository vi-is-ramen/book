cargo-inherit – CLI Для Inherit

Добро пожаловать в cargo-inherit — инструмент командной строки, который превращает любой репозиторий Git в многоразовый, настраиваемый шаблон проекта. Если Вы когда-либо копировали шаблонный проект, а затем вручную заменяли все заполнители, этот инструмент для Вас.

cargo-inherit — это тонкая, но мощная обертка над inherit-core. Она добавляет:

  • Обнаружение шаблонов – из GitHub или любой Git ссылки.
  • Псевдонимы – короткие имена для длинных путей к шаблонам.
  • Значения по умолчанию – предварительно заполняемые переменные, такие как AUTHOR.
  • Умное кеширование – клонированные шаблоны сохраняются для повышения скорости.
  • Интерактивные запросы – запросы для недостающих переменных с удобными значениями по умолчанию для повышения скорости.
  • Хуки после создания – запуск команд оболочки после создания проекта. (напр. cargo fmt, git add .)
  • Файл конфигурации – храните свои секреты и предпочтения в безопасности.

Давайте погружаться!

Установка

cargo-inherit - это бинарный файл Rust. Установите его из crates.io:

cargo install cargo-inherit

Убедитесь, что ~/.cargo/bin присутствует в Вашей переменной PATH. После установки, команда будет cargo inherit.

Замечание: бинарник называется cargo-inherit, но в примерах в этой статьи будет писаться просто inherit для краткости. На практике Вы сможете запускать cargo inherit.

Быстрый Старт

Создание новой Rust-библиотеки из гипотетического шаблона cargo-lib:

inherit rust-lib/cargo-lib to my-project

Inherit:

  1. Склонирует https://github.com/rust-lib/cargo-lib (и закеширует для последующего использования).
  2. Прочитает Inherit.toml и просканирует файлы для @ПЕРЕМЕННЫХ@.
  3. Спросит у Вас значения (с полезными описаниями и значениями по умолчанию).
  4. Сгенерирует my-project/, заменив все плейсхолдеры.
  5. Запустит git init и выполнит post_create хуки.

Если у Вас есть локальная папка с шаблоном, Вы можете использовать file:// ссылку или полный путь:

inherit /home/me/my-templates/rust-lib

Справочник Команд

generate – Главное Событие

Синтаксис: inherit <template> [to <directory>]

  • template – может быть:
    • user/repo (скращение для GitHub)
    • полный URL (https://..., file://..., или полный путь)
    • псевдоним (см. ниже)
  • directory – где создать сам проект (по умолчанию текущая рабочая директория)

Пример:

inherit alice/awesome-template to my-app

Если alice/awesome-template требует переменные по типу PROJECT_NAME и AUTHOR, Вас спросят интерактивно. Значения из Вашей таблицы [defaults] будут предложены как подсказки (Enter для применения).

alias – Дайте Любимым Шаблонам Удобные Имена

КомандаОписание
inherit <template> to alias <name>Создать псевдоним для шаблона
inherit alias listПоказать все псевдонимы
inherit alias remove <name>Удалить псевдоним

Пример:

# Добавить псевдоним
inherit rust-lib/cargo-lib to alias rlib

# Использовать его позднее
inherit rlib to new-project

# Посмотреть все псевдонимы
inherit alias list

# Удалить псевдоним
inherit alias remove rlib

Псевдонимы хранятся в Вашем конфигурационном файле в словаре [aliases].

default – Предустановленные Значения Переменных

КомандаОписание
inherit default for <VAR>Установить значение по умолчанию для переменной
inherit default listПоказать все значения по умолчанию
inherit default unset <VAR>Удалить значение по умолчанию

В качестве первоначального варианта при появлении запроса используются значения по умолчанию. Вы можете изменить их, введя другое значение.

Пример:

# Установите своё имя единожды
inherit default for AUTHOR
# > спросит: "Default value for AUTHOR [Your Name <you@example.com>]:"
# Введите новое значение или нажмите Enter, чтобы сохранить текущее.

# Впоследствии каждый шаблон, запрашивающий AUTHOR, будет предлагать это значение.

Значения по умолчанию хранятся в словаре [defaults] Вашего конфигурационного файла.

cache – Управляйте Скачанными Шаблонами

КомандаОписание

После первого клонирования шаблоны кэшируются. Это ускоряет последующие генерации и позволяет использовать их в автономном режиме. Каталог кэша можно настроить (см. ниже).

Файл Конфигурации

При первом запуске cargo-inherit создаёт конфигурационный файл по следующему пути:

  • Linux / macOS: ~/.config/inherit/config.toml
  • Windows: %APPDATA%\inherit\config.toml

Вы можете переопределить местоположение с помощью переменной среды INHERIT_CONFIG.

Вот полный пример с пояснениями:

# Значения по умолчанию для переменных шаблона.
# Если шаблон требует переменную, указанную здесь, ее значение используется в качестве
# предложения по умолчанию — Вы все еще можете переопределить его через интерактивную подсказку.
[defaults]
AUTHOR = "Your Name <you@example.com>"
VERSION = "0.1.0"

# Псевдонимы для шаблонов
[aliases]
rlib = "rust-lib/cargo-lib"
blog = "https://github.com/my/blog-template.git"

# Каталог, используемый для кэширования загруженных шаблонов.
# Поддерживает расширение ~/.
cache_dir = "~/.cache/inherit"

# Персональный токен доступа GitHub (для приватных репозиториев).
# Должен иметь область действия "repo".
github_token = "ghp_..."

# Следует ли автоматически запускать `git init` в сгенерированных проектах.
init_git = true

# Следует ли выполнять хуки `post_create`, определенные шаблонами.
run_hooks = true

# Команда для открытия проекта после генерации (например, "code", "nvim", "idea").
# Например, я поставил сюда nvim, что весьма удобно: одной командой и проект создал,
# и сразу же IDE открыл.
open_with = "code"

Переменные Окружения

ПеременнаяОписание
INHERIT_CONFIGПолный путь к файлу конфигурации (переопределяет значение по умолчанию)
INHERIT_CACHE_DIRКаталог для кэшированных шаблонов (переопределяет cache_dir)
INHERIT_NON_INTERACTIVEЕсли установлено значение 1, запрос никогда не будет выполняться — ошибка возникает, если отсутствуют значения по умолчанию.

Неинтерактивный режим полезен в системах непрерывной интеграции или скриптах. Пример:

INHERIT_NON_INTERACTIVE=1 inherit user/repo to output

Как Это Работает Изнутри

Когда Вы запускаете inherit user/repo:

  1. Разрешение – ``user/repo преобразуется в URL-адрес Git (https://github.com/user/repo.git`), если это не псевдоним или полный URL-адрес.
  2. Получение – Команда git clone --depth 1 используется для загрузки шаблона в кэш (с указанием канонического URL). При последующих запусках используется кэшированная копия.
  3. Загрузка – inherit-core считывает Inherit.toml и сканирует все файлы на наличие заполнителей @VAR@, соблюдая при этом .inherignore.
  4. Опрос – Для каждой найденной переменной CLI отображает подсказку с ее описанием (из [variables]) и заданным значением по умолчанию (из [defaults]).
  5. Обработка – Все файлы и папки копируются в целевой каталог, при этом @VAR@ заменяется как в содержимом, так и в именах файлов. Бинарные файлы копируются без изменений.
  6. Финализация – Если init_git = true, в целевом объекте выполняется новая инициализация git init. Затем выполняются все хуки post_create из шаблона (с использованием sh -c в Unix, cmd /C в Windows).
  7. Открытие – Если параметр open_with задан, интерфейс командной строки запускает эту команду, передавая целевой каталог в качестве аргумента.

Манифест Шаблона (Inherit.toml)

Пример для гипотетического шаблона cargo-lib:

[template]
name = "cargo-lib"
description = "Minimal Rust library template"

[variables]
PROJECT_NAME = "Name of the project"
AUTHOR = "Author name and email"
VERSION = "Initial version"
DESCRIPTION = "Short description of the library"

[hooks]
post_create = ["cargo fmt", "git add ."]
  • [variables] ключи — это заполнители (без символа @); значения — это описания, отображаемые пользователю.
  • post_create команды, выполняющиеся в сгенерированном каталоге проекта.

Файл .inherignore

Ровно такой же, как .gitignore, но исключает файлы из шаблона. Пример:

target/
Cargo.lock
.git/

Любой файл или папка, соответствующие этим шаблонам, не будут скопированы в новый проект. Это позволяет избежать появления артефактов сборки или специфичных для инструмента элементов в вашем шаблоне.

Расширенные Темы

Использование Приватных Репозиториев GitHub

Укажите параметр github_token в Вашем файле конфигурации. Токен будет добавлен в URL-адрес клонирования:

https://<token>@github.com/user/repo.git

Убедитесь, что Ваш токен имеет как минимум область действия repo.

Локальные Шаблоны без Git

Вы можете указать непосредственно на каталог:

inherit /absolute/path/to/template

Инструмент не будет пытаться клонировать его; он будет использовать каталог как есть. Это идеально подходит для быстрой итерации.

Поведение Кеширования

  • Каждый шаблон кэшируется под стабильным идентификатором, полученным из его канонического URL-адреса.
  • Команда git clone --depth 1 используется для поддержания небольшого размера кэша.
  • Чтобы обновить кэшированный шаблон, удалите его из кэша (команда inherit cache clean удалит все данные) или вручную выполните команду git pull в каталоге кэша.

Безопасность Хуков После Создания

Хуки — это всего лишь команды оболочки. Они выполняются с теми же привилегиями, что и пользователь. Используйте их ответственно — не клонируйте ненадежные шаблоны, не проверив их файл Inherit.toml.

Собираем Всё Воедино – Реальный Рабочий Процесс

Представьте, что Вы используете корпоративный шаблон для микросервисов:

  1. Создайте шаблон в репозитории mycorp/microservice-template.

  2. Добавьте псевдонимы для вашей команды:

    inherit mycorp/microservice-template to alias mcsrv

  3. Установите параметры компании по умолчанию:

    inherit default for AUTHOR
# -> напечатайте "Engineering Team <eng@mycorp.com>"
inherit default for LICENSE
# -> напечатайте "MIT OR Apache-2.0"

  4. Создайте новый сервис:

    inherit mcsrv to payment-service

    Инструмент запросит только специфичные для проекта переменные (например, SERVICE_NAME, PORT). Настройки по умолчанию для компании уже заполнены.

  5. Автоматическое открытие в VS Code и запуск cargo build через хук – Ваша команда начнет работу за считанные секунды.

Какую Проблему Решает Библиотека?

Копирование-вставка шаблонного проекта приводит к устаревшим копиям, несогласованным именованиям и утомительному поиску-и-замене. Лучший подход:

  • Хранить исходный шаблон с заполнителями, такими как @PROJECT_NAME@.
  • Позволить инструменту сканировать шаблон, чтобы обнаружить, какие переменные необходимы.
  • Спросить пользователя (или скрипт) о конкретных значениях.
  • Сгенерировать новый проект, во всех заполнителях будет произведена замена – включая имена файлов и имена папок!

inherit-core реализует именно этот конвейер, оставаясь полностью независимым от пользовательского интерфейса. Инструмент командной строки cargo-inherit использует его для интерактивного опроса, но Вы также можете управлять им из сборочного скрипта или графического интерфейса.

Модули в деталях

error.rs – Чёткие, пригодные для действия ошибки

Все операции, которые могут завершиться неудачей, возвращают Result<T, InheritError>. Перечисление ошибок различает:

  • Отсутствие манифеста (ManifestNotFound)
  • Ошибки разбора (ManifestParse)
  • Отсутствующие переменные (MissingVariables)
  • Ошибки ввода-вывода и выполнения команд
#![allow(unused)]
fn main() {
pub enum InheritError {
    Io(#[from] std::io::Error),
    ManifestNotFound(PathBuf),
    ManifestParse(#[from] toml::de::Error),
    MissingVariables(Vec<String>),
    InvalidVariable(String),
    CommandFailed { cmd: String, status: ExitStatus },
    KissReplace(#[from] kissreplace::KissReplaceError),
}
}

manifest.rs – Конфигурация шаблона

Десериализует Inherit.toml с тремя опциональными секциями:

[template]
name = "cargo-lib"
description = "Минимальный шаблон библиотеки Rust"

[variables]
PROJECT_NAME = "Имя проекта"
AUTHOR = "Имя и email автора"

[hooks]
post_create = ["cargo fmt", "echo 'Готово!'"]

Карта variables служит двум целям:

  • Она определяет, какие переменные ожидает шаблон (дополнительные переменные, найденные в файлах, также становятся обязательными).
  • Строковое значение является описанием (показывается пользователю при запросе).

#[serde(default)] делает каждое поле опциональным – шаблон может вообще не иметь манифеста (хотя тогда вы потеряете описания и хуки).

ignore.rs – Что пропускать

inherit-core учитывает два уровня игнорирования:

  1. Всегда игнорируется – "Inherit.toml", ".inherignore", ".git" (и всё внутри .git/).
  2. Определяется пользователем – через файл .inherignore в корне шаблона, с синтаксисом .gitignore.
#![allow(unused)]
fn main() {
let ignore = InheritIgnore::load(template_dir);
if ignore.is_ignored(relative_path, is_dir) {
    continue; // пропустить этот файл/папку
}
}

Вы можете исключать артефакты сборки, lock-файлы или любой генерируемый контент, который не должен копироваться в новые проекты.

scanner.rs – Обнаружение переменных

Сканер обходит каталог шаблона (с учётом игнорирования) и читает каждый текстовый файл. Он использует kissreplace::scan::extract_vars для поиска всех заполнителей вида @...@. Результатом является HashSet<String> имён обязательных переменных.

Зачем сканировать? Потому что автор шаблона может забыть перечислить переменную в [variables]. Сканер гарантирует, что ничего не пропущено – объединение объявленных в манифесте и найденных сканером переменных становится финальным обязательным набором.

pipeline.rs – Сердце операции

Две публичные функции управляют всем процессом:

load_template(source_dir: &Path) -> Result<TemplateContext>

Возвращает TemplateContext, содержащий:

  • Разобранный Manifest
  • required_vars – все переменные, которые должны быть в итоге предоставлены
  • var_descriptions – описания из манифеста (пустая строка, если не объявлено)

Вы вызываете эту функцию первой, чтобы показать пользователю список того, что ему нужно заполнить.

process_template(source_dir, target_dir, final_vars, opts) -> Result<ProcessResult>

Это настоящая рабочая лошадка. Она:

  • Проверяет имена переменных (должны соответствовать ^[A-Z][A-Z0-9_]*$ – по правилам kissreplace).
  • Проверяет, что все необходимые переменные присутствуют и не пусты.
  • Создаёт целевой каталог.
  • Обходит исходный каталог, соблюдая всегда игнорируемые и записи из .inherignore.
  • Для каждого файла:
    • Если это каталог -> создать его в целевом каталоге (после замены заполнителей в его имени).
    • Если это файл:
      • Попытаться прочитать как UTF‑8 -> заменить заполнители в содержимом, записать как текст.
      • При ошибке (двоичный файл) -> скопировать побайтово (без замены).
  • Если opts.init_git равно true -> запускает git init -q в целевом каталоге.
  • Если opts.run_hooks равно true -> выполняет каждую команду post_create по порядку.

Функция возвращает количество обработанных текстовых файлов и скопированных двоичных файлов.

Собираем всё вместе – полный пример

Давайте смоделируем, что сделал бы инструмент командной строки. Мы будем использовать гипотетический пример шаблона cargo-lib.

use inherit_core::{load_template, process_template, ProcessOptions, Variables};
use std::fs;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let template_dir = "./examples/cargo-lib";
    let target_dir = "./my-new-lib";

    // 1. Загружаем шаблон, чтобы узнать, какие переменные нужны
    let ctx = load_template(template_dir.as_ref())?;
    println!("Необходимые переменные: {:?}", ctx.required_vars);

    // 2. Собираем значения (обычно Вы спросили бы пользователя)
    let mut vars = Variables::new();
    vars.insert("PROJECT_NAME".into(), "my_awesome_lib".into());
    vars.insert("AUTHOR".into(), "Jane Doe <jane@example.com>".into());
    vars.insert("VERSION".into(), "0.1.0".into());
    vars.insert("DESCRIPTION".into(), "Делает что-то крутое".into());

    // 3. Обрабатываем шаблон
    let opts = ProcessOptions::default(); // init_git = true, run_hooks = true
    let result = process_template(
        template_dir.as_ref(),
        target_dir.as_ref(),
        &vars,
        opts,
    )?;

    println!("Сгенерировано {} текстовых файлов, {} двоичных файлов", 
             result.processed_files, result.binary_files);

    // Проверяем, что заполнители исчезли
    let cargo_toml = fs::read_to_string(target_dir.join("Cargo.toml"))?;
    assert!(!cargo_toml.contains('@'));

    Ok(())
}

Когда Вы запустите этот код, целевой каталог будет содержать свежий проект библиотеки Rust с name = "my_awesome_lib" и папкой .git (потому что init_git по умолчанию равен true).

Продвинутые возможности

Заполнители в именах файлов и папок

Замена не ограничивается содержимым файлов – она также применяется к путям. Этот файл шаблона:

src/@PROJECT_NAME@/mod.rs

будет создан как src/my_awesome_lib/mod.rs. Очень полезно для языко-специфичных структур (например, пакетов Python, пространств имён Java).

Двоичные файлы копируются без изменений

Если файл не может быть прочитан как UTF‑8, inherit-core считает его двоичным и выполняет побайтовое копирование. Замена заполнителей не производится, поэтому ваши изображения или скомпилированные ресурсы остаются нетронутыми.

Хуки после создания на Windows и Unix

Команды hooks.post_create выполняются с использованием:

  • sh -c "команда" на Unix
  • cmd /C "команда" на Windows

Это даёт максимальную переносимость. Типичный хук может запускать cargo fmt, git add . или npm install.

Обработка ошибок на практике

Инструмент командной строки использует InheritError для вывода понятных пользователю сообщений. Например:

  • MissingVariables – выводит список переменных, которые пользователь забыл предоставить.
  • CommandFailed – показывает, какой хук завершился ошибкой, и его код выхода.
  • ManifestNotFound – предполагает, что путь, возможно, не является действительным каталогом шаблона.

Поскольку каждая ошибка реализует std::error::Error, вы можете использовать anyhow или thiserror в своей собственной обёртке.

Стратегия тестирования

Крейт включает интеграционные тесты, которые:

  • Запускают пример шаблона cargo-lib от начала до конца.
  • Проверяют, что отсутствующие переменные вызывают правильную ошибку.
  • Тестируют замену переменных внутри имён файлов (случай test_variable_in_filename).

Эти тесты используют tempfile::tempdir() для избежания загрязнения дерева исходных кодов. Они также отключают init_git и хуки, чтобы тесты оставались быстрыми и детерминированными.

Почему kissreplace?

Движок заполнителей намеренно сделан крошечным и быстрым. kissreplace предоставляет:

  • Сканирование – извлечение всех имён @VAR@ из строки.
  • Замену – эффективную, однопроходную подстановку.

Его философия «kiss» идеально соответствует inherit-core: никакой магии регулярных выражений, никаких случайных частичных замен, только чёткая семантика.

Когда использовать inherit-core напрямую

Вы можете обойти cargo-inherit CLI, если хотите:

  • Интегрировать шаблонизацию в большую сборочную систему (например, генератор рабочего пространства).
  • Предоставить другой пользовательский интерфейс – TUI, веб-форму или генерацию, управляемую переменными окружения.
  • Автоматизировать создание экземпляров шаблонов в конвейерах CI/CD.

Просто добавьте inherit-core как зависимость, и вы получите весь механизм шаблонизации без интерактивной нагрузки.

cargo add inherit-core

Она учитывает файлы игнорирования, заменяет заполнители везде (даже в путях) и запускает хуки для финализации сгенерированного проекта. Kissreplace: Минималистичный шаблонизатор

Добро пожаловать в kissreplace – крошечный, без лишних сложностей шаблонизатор, который следует принципу KISS (Keep It Simple, Stupid! – Делай проще, дурак!). Если Вам нужно заменять заполнители вида @VAR@ в строках, путях к файлам или целых коллекциях, этот крейт делает именно это и ничего больше. Никаких сложных DSL, никаких нежелательных накладных расходов во время выполнения – только простая, предсказуемая подстановка.

Что Он Делает?

  • Находит каждое вхождение @VAR@ в строке, где VAR соответствует простому правилу именования (буквы, цифры, символ подчёркивания и должен начинаться с буквы или подчёркивания).
  • Заменяет его значением из хеш-карты (HashMap<String, String>).
  • Оставляет недопустимые или отсутствующие переменные нетронутыми (например, @123@, @var-name@ или @UNKNOWN@ остаются как есть).
  • Работает с отдельными строками, целыми векторами (на месте или по значению) и путями к файлам.

Быстрый старт

#![allow(unused)]
fn main() {
use std::collections::HashMap;
use kissreplace::{KissReplace, Variables};

let mut vars = Variables::new();
vars.insert("NAME".to_string(), "World".to_string());
vars.insert("PROJECT".to_string(), "kissreplace".to_string());

let template = "Hello @NAME@, you're reading @PROJECT@ docs!";
let result = vars.replace_str(template);
println!("{}", result);
// Вывод: Hello World, you're reading kissreplace docs!
}

Под капотом Variables – это просто псевдоним типа для HashMap<String, String>, так что Вы можете создавать её любым удобным способом.

Как Работает Замена

Функция replace_str сканирует входные данные слева направо:

  1. Ищет следующий символ '@'.
  2. Начиная с этой позиции, ищет вперед закрывающий '@'.
  3. Проверяет, является ли текст между ними допустимым именем переменной.
  4. Если да – заменяет его значением из карты (или оставляет @VAR@, если переменная отсутствует).
  5. Если нет – обрабатывает первый '@' как литеральный символ и продолжает сканирование.

Поскольку сканирование однопроходное и рекурсивное раскрытие не выполняется, переменные, выглядящие как вложенные, например @A@, где A указывает на "@B@", не раскрываются далее – вы получаете ровно одну подстановку на заполнитель.

Допустимые Имена Переменных

  • Не должны быть пустыми.
  • Первый символ должен быть буквой ASCII (a-z, A-Z) или подчёркиванием _.
  • Последующие символы могут быть буквами ASCII, цифрами (0-9) или подчёркиванием.
#![allow(unused)]
fn main() {
use kissreplace::valid::is_valid_var_name;

assert!(is_valid_var_name("PROJECT_2"));
assert!(is_valid_var_name("_private"));
assert!(!is_valid_var_name("123start"));
assert!(!is_valid_var_name("with-dash"));
}

Трейт KissReplace

Этот трейт реализован для Variables (HashMap<String, String>) и предоставляет несколько удобных методов:

МетодОписание
replace_str(&self, input: &str) -> StringОсновной метод – заменяет заполнители в одной строке.
replace(&self, sources: Vec<String>) -> Vec<String>Применяет замену к каждому элементу вектора, возвращая новый вектор.
replace_mut(&self, sources: &mut Vec<String>)Версия на месте – более эффективна по выделению памяти.
replace_paths(&self, paths: Vec<PathBuf>) -> Vec<PathBuf>Работает с путями к файлам (преобразует в строку, заменяет, затем обратно в PathBuf).

Пример: Замена Многих Строк

#![allow(unused)]
fn main() {
let vars = /* ... */;
let mut lines = vec![
    "name = @NAME@".to_string(),
    "version = @VERSION@".to_string(),
];
vars.replace_mut(&mut lines);
// lines теперь содержит заменённые значения
}

Пример: Пути к Файлам

#![allow(unused)]
fn main() {
let vars = /* ... */;
let paths = vec![
    PathBuf::from("src/@PROJECT@/main.rs"),
    PathBuf::from("config/@PROJECT@.toml"),
];
let new_paths = vars.replace_paths(paths);
}

Сканирование Переменных

Если Вам нужно узнать только какие переменные встречаются в шаблоне (без их замены), используйте scan::extract_vars:

#![allow(unused)]
fn main() {
use kissreplace::scan;

let template = "Hello @NAME@, your @PROJECT@ is version @VERSION@";
let vars = extract_vars(template);
// vars = {"NAME", "PROJECT", "VERSION"}
}

Функция возвращает HashSet<String> уникальных допустимых имён переменных, найденных в тексте. Логика сканирования точно такая же, как в replace_str, поэтому можно доверять, что сообщённые имена будут заменены при последующем вызове replace_str.

Обработка Ошибок

Крейт определяет собственное перечисление KissReplaceError. В настоящее время существуют два варианта:

  • InvalidVariableName(String) – возвращается функциями, проверяющими имена (если Вы создаёте свою собственную логику проверки).
  • InvalidUtf8 – используется, когда преобразование PathBuf в строку завершается неудачей (путь не является допустимым UTF‑8).

Большинство методов замены не возвращают Result (они безошибочны). Ошибки появляются только если Вы явно вызываете функции из модуля valid или обрабатываете пути с не‑UTF‑8 компонентами.

#![allow(unused)]
fn main() {
use kissreplace::{KissReplaceError, valid};

if let Err(e) = some_validation_function("1invalid") {
    println!("Ошибка: {}", e);
}
}

Async Возможность

Когда Вы включаете возможность async, крейт подтягивает tokio как опциональную зависимость. Сама логика замены синхронна – эта возможность просто делает tokio доступным для ваших собственных асинхронных задач ввода-вывода, например:

  • Чтение сотен файлов шаблонов конкурентно с помощью tokio::fs.
  • Замена переменных в каждом файле и запись результатов.

Ничто в kissreplace само по себе не является async, но возможность позволяет содержать список зависимостей в порядке, если вы уже используете tokio.

Соображения Производительности

  • Однопроходное сканирование входных данных – время O(n).
  • replace_mut повторно использует существующую ёмкость Vec, уменьшая количество выделений памяти при обработке многих строк.
  • Сканер для extract_vars также выполняет однопроходное сканирование и использует HashSet для хранения уникальных имён.

Если Вам нужно заменить один и тот же шаблон сотни раз с разными наборами переменных, рассмотрите предварительное сканирование имён переменных и последующую замену через String::replace или ручной цикл – но для большинства случаев использования прямой вызов replace_str вполне подходит.

Философия – Почему KISS?

Многие шаблонизаторы разрастаются органически: условия, циклы, фильтры, подшаблоны… и внезапно ваш «простой» шаблонизатор становится полноценным языком. kissreplace намеренно останавливается на подстановке заполнителей. Он идеален для:

  • Генерации конфигурационных файлов (например, config.@ENV@.toml -> config.production.toml)
  • Простых шаблонов электронных писем или уведомлений
  • Раскрытия переменных окружения в пользовательских CLI
  • Обучения концепции шаблонизации без отвлекающих факторов

Если вам нужна логика, вы всегда можете объединить его с собственными управляющими конструкциями Rust – это сохраняет простым как синтаксис шаблонов, так и ваш код.

Ленивая Загрузка, Умное Кэширование: Крейт lazyget

Добро пожаловать в руководство по lazyget! Если Вы когда-либо ловили себя на том, что снова и снова перекачиваете один и тот же огромный ресурс, или копируете-вставляете хрупкий код кэширования между проектами, Вы обратились по адресу.

lazyget — это крошечный, но мощный крейт Rust, который решает большую проблему: как получить артефакт (файл, двоичный файл, набор данных — что угодно) один раз, закэшировать его локально и больше никогда об этом не беспокоиться.

Он делает одну вещь и делает её хорошо: учитывая каталог кэша и идентификатор артефакта, он либо вернёт существующий путь к кэшированному файлу, либо Выполнит вашу пользовательскую логику получения ровно один раз, сохранит результат и вернёт Вам путь – всё это с атомарными обновлениями и автоматической очисткой при сбое.

Давайте погрузимся.

Какую Проблему Решает lazyget?

Представьте, что Вы пишете инструмент командной строки, которому нужен большой файл AI-модели, игровой движок, который загружает наборы ресурсов, или сборочный скрипт, который подтягивает конкретный инструментарий. Вы хотите:

  • Никаких избыточных загрузок – если артефакт уже на диске, просто используйте его.
  • Никакого устаревшего кэша – иногда Вы должны обновить артефакт.
  • Никаких наполовину записанных файлов – если загрузка не удалась, старая (или частичная) версия никогда не должна использоваться.
  • Никакого шаблонного кода – Вы не должны каждый раз писать танцы с временными каталогами и обработку ошибок.

lazyget обрабатывает всё это за вас. Вы просто указываете ему, как получить артефакт (замыкание или асинхронную функцию), а он позаботится об остальном.

Быстрый Старт

Добавьте lazyget в ваши зависимости:

cargo add lazyget

Если Вам нужна асинхронная поддержка (с использованием tokio), включите возможность async:

cargo add lazyget --features async

Синхронный Пример

#![allow(unused)]
fn main() {
use lazyget::{fetch, make_id};
use std::fs;
use std::path::Path;

// Где хранить кэшированные артефакты (здесь: системный каталог кэша)
let cache_dir = dirs::cache_dir().unwrap().join("my-app");

// Стабильный ID для вашего артефакта – может осноВываться на URL и хеше коммита
let id = make_id("https://github.com/example/model", Some("v1.2.3"));

let artifact_path = fetch(&cache_dir, &id, |temp_dir: &Path| {
    // Это замыкание Выполняется, только если артефакт ЕЩЁ НЕ закэширован.
    // `temp_dir` – это черновой каталог, который станет финальным расположением кэша.
    // Загрузите или сгенерируйте ваш артефакт здесь:
    let response = ureq::get("https://example.com/model.bin").call()?;
    let mut reader = response.into_reader();
    let mut file = fs::File::create(temp_dir.join("model.bin"))?;
    std::io::copy(&mut reader, &mut file)?;
    Ok(())
})?;

println!("Артефакт готов по адресу: {}", artifact_path.display());
}

Если Вы запустите это дважды, замыкание Выполнится только в перВый раз. Второй Вызов немедленно вернёт кэшированный путь.

Асинхронный Пример (с tokio)

Включите возможность async и используйте async_fetch:

#![allow(unused)]
fn main() {
use lazyget::async_fetch;
use tokio::fs;
use tokio::io::AsyncWriteExt;

    let response = reqwest::get(url).await?;
    let bytes = response.bytes().await?;

    file.write_all(&bytes).await?;
    Ok(())

}

Основные Понятия

1. Идентификатор Артефакта

Каждый артефакт идентифицируется именем каталога внутри вашего корня кэша. Самый простой способ — использовать человекочитаемую строку:

#![allow(unused)]
fn main() {
let id = "my-cool-model-v2";
}

Но Вы также можете сгенерировать детерминированный хеш из URL и опционального тега (например, коммита Git) с помощью make_id:

#![allow(unused)]
fn main() {
let id = make_id("https://github.com/example/repo", Some("abc123def"));
// => "a6b4c3e2..."  (64 шестнадцатеричных символа)
}

make_id Вычисляет SHA‑256 от url + ":" + tag (если тег Some). Это идеально, когда источник вашего артефакта меняется со временем, и Вы хотите автоматически инвалидировать кэш.

2. fetch / async_fetch – Ленивая Рабочая Лошадка

#![allow(unused)]
fn main() {
fn fetch<P, F>(cache_dir: P, artifact_id: &str, fetch_fn: F) -> Result<PathBuf>
where
    P: AsRef<Path>,
    F: FnOnce(&Path) -> Result<(), Box<dyn Error + Send + Sync>>,
}

Поведение:

  • Проверить, существует ли cache_dir/artifact_id.
  • Если да -> немедленно вернуть его путь.
  • Если нет:
    • Создать временный каталог .artifact_id-tmp внутри cache_dir.
    • Вызвать fetch_fn с этим временным каталогом.
    • Если fetch_fn успешен -> атомарно переименовать временный каталог в финальное имя.
    • Если fetch_fn завершается ошибкой -> удалить временный каталог и распространить ошибку.

Это гарантирует, что Вы никогда не увидите частично записанный или повреждённый артефакт.

3. refetch / async_refetch – Принудительное Обновление

Иногда Вы хотите игнорировать существующий кэш и получить артефакт заново, даже если он присутствует. Именно для этого предназначен refetch:

#![allow(unused)]
fn main() {
fn refetch<P, F>(cache_dir: P, artifact_id: &str, fetch_fn: F) -> Result<PathBuf>
}

Он удаляет существующий кэшированный каталог (если есть), а затем внутренне Вызывает fetch.

Обработка Ошибок

Все операции, которые могут завершиться неудачей, возвращают Result<T, LazyGetError>. LazyGetError — это перечисление thiserror, охватывающее:

  • Io – ошибки ввода-Вывода (файловая система).
  • Fetch – ваше собственное замыкание вернуло ошибку (обёрнуто в трейт-объект Box).
  • CacheCreate – не удалось создать корневой каталог кэша.
  • AtomicRename – финальный шаг переименования не удался (очень редко, но возможно на некоторых файлоВых системах).

Это означает, что Вы можете использовать сопоставление с образцом для обработки конкретных случаев или использовать ?, чтобы пробросить ошибки наверх.

#![allow(unused)]
fn main() {
use lazyget::{LazyGetError, fetch};

match fetch(cache_dir, "my-id", |dir| Ok(())) {
    Ok(path) => println!("Получен {}", path.display()),
    Err(LazyGetError::Fetch(e)) => eprintln!("Логика загрузки не удалась: {}", e),
    Err(e) => eprintln!("Ошибка системы кэширования: {}", e),
}
}

Под Капотом: Как Работает Атомарное Кэширование

lazyget следует простому, но надёжному протоколу:

  1. Проверка существования – Если target_dir существует, мы закончили.
  2. Подготовка временного каталога – cache_dir/.artifact_id-tmp. Если он уже существует от предыдущего прерванного запуска, он удаляется.
  3. Выполнение вашей загрузки – Вы записываете файлы во временный каталог. Если Вам нужно загрузить несколько файлов или распаковать архив, делайте это там.
  4. Фиксация – std::fs::rename (или tokio::fs::rename). На большинстве файлоВых систем это атомарно – либо переименование происходит, либо нет. Ни один читатель никогда не увидит неполный каталог.
  5. Очистка – Если ваше замыкание возвращает ошибку, временный каталог удаляется автоматически.

Этот подход работает на Linux, macOS и Windows.

Полный Пример: Загрузка Zip-Архива

Вот реальный синхронный пример, который загружает zip-файл, извлекает его и кэширует результат:

#![allow(unused)]
fn main() {
use lazyget::{fetch, make_id, LazyGetError};
use std::fs::File;
use std::io::{Cursor, Read};
use std::path::Path;
use zip::ZipArchive;

fn fetch_and_extract(temp_dir: &Path) -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
    // Загрузка zip
    let mut resp = ureq::get("https://example.com/assets.zip").call()?;
    let mut bytes = Vec::new();
    resp.into_reader().read_to_end(&mut bytes)?;

    // Распаковка в temp_dir
    let mut archive = ZipArchive::new(Cursor::new(bytes))?;
    for i in 0..archive.len() {
        let mut file = archive.by_index(i)?;
        let out_path = temp_dir.join(file.mangled_name());
        if file.is_dir() {
            std::fs::create_dir_all(&out_path)?;
        } else {
            let mut outfile = File::create(&out_path)?;
            std::io::copy(&mut file, &mut outfile)?;
        }
    }
    Ok(())
}

let cache_dir = std::env::temp_dir().join("my-cache");
let id = make_id("https://example.com/assets.zip", Some("v2"));
let path = fetch(&cache_dir, &id, fetch_and_extract)?;
println!("Ресурсы готоВы по адресу: {}", path.display());
}

Стратегии Тестирования

lazyget легко тестировать, потому что Вы можете передать любой FnOnce – в том числе тот, который подсчитывает, сколько раз он был Вызван. Сам крейт использует tempfile::tempdir() для создания временных корней кэша для тестов.

Пример шаблона тестирования:

#![allow(unused)]
fn main() {
#[test]
fn test_caching_behaviour() {
    let tmp = tempfile::tempdir().unwrap();
    let id = "test-id";
    let mut counter = 0;

    // ПерВый Вызов: Выполняет замыкание
    let _ = fetch(tmp.path(), id, |_dir| { counter += 1; Ok(()) }).unwrap();
    assert_eq!(counter, 1);

    // Второй Вызов: использует кэш
    let _ = fetch(tmp.path(), id, |_dir| { counter += 1; Ok(()) }).unwrap();
    assert_eq!(counter, 1);
}
}

Возможности (feature flags)

  • default – никаких дополнительных возможностей.
  • async – добавляет зависимость tokio и предоставляет async_fetch / async_refetch. Вы получаете tokio::fs и tokio::process, но среда Выполнения не запускается автоматически – Вам нужна среда Выполнения Tokio в вашем приложении.

Когда не следует использовать lazyget

  • Вам нужно кэшировать очень большое количество крошечных файлов (накладные расходы на каталог артефакта минимальны, но если у вас миллионы файлов, рассмотрите базу данных).
  • Вы пишете для окружения no_std (этот крейт интенсивно использует std).

Заключение

lazyget предоставляет Вам надёжное, атомарное, ленивое кэширование с API, которое умещается в голове. Это такой крейт, который исчезает в вашем коде – Вы замечаете его только тогда, когда он работает идеально.

wrapc: Разбор аргументов rustc для инструментов RUSTC_WRAPPER

Обзор

Когда вы создаёте инструмент, который перехватывает компиляцию Rust — будь то кэш компиляции, пользовательский профайлер, статический анализатор или инжектор флагов компоновщика — вам неизбежно понадобится разбирать аргументы командной строки rustc.

Это сложнее, чем кажется.

CLI rustc — подвижная цель: он смешивает значения с = и через пробел, содержит сложный подсинтаксис для компоновки (-l static:+bundle,+whole-archive=name:renamed) и постоянно развивается с флагами, доступными только в nightly. Универсальные парсеры CLI, такие как clap, слишком жёсткие, слишком тяжёлые и принципиально не подходят для протокола обёрток.

wrapc существует именно для решения этой проблемы.

Он предоставляет строго типизированный, осведомлённый о протоколе парсер, который:

  • Понимает формат вызова Cargo: <wrapper> - <rustc> <args...>
  • Разбирает сложные флаги в структурированные типы Rust (--emit, --extern, -L, -l и т.д.)
  • Гарантирует безупречное восстановление с помощью Info::to_args()
  • Корректно обрабатывает неизвестные / nightly-флаги, помещая их в info.unknown
  • Избегает паник на краевых случаях, таких как разделитель - или пропущенные значения

Короче: wrapc позволяет вам сосредоточиться на том, что ваша обёртка делает, а не на борьбе с разбором аргументов.

Быстрый старт

Добавьте зависимость:

cargo add wrapc

Затем в вашем main.rs обёртки:

use std::process::Command;
use wrapc::fetch;

fn main() {
    // 1. Разбираем `std::env::args()` в соответствии с протоколом обёртки
    let mut info = fetch().expect("Не удалось разобрать аргументы rustc");

    // 2. Обрабатываем сквозные команды на раннем этапе (help/version/sysroot probes)
    if info.help || info.version || info.print.is_some() {
        let rustc = info.rustc.unwrap_or_else(|| "rustc".to_string());
        let status = Command::new(rustc)
            .args(info.to_args())
            .status()
            .expect("Не удалось запустить rustc");
        std::process::exit(status.code().unwrap_or(1));
    }

    // 3. Анализируем или изменяем контекст компиляции
    if info.crate_name.as_deref() == Some("legacy_crate") {
        info.codegen_opts.push("opt-level=1".to_string());
    }

    // 4. Определяем реальный путь к rustc и восстанавливаем аргументы
    let rustc_path = info.rustc.unwrap_or_else(|| "rustc".to_string());
    let args = info.to_args();

    // 5. Запускаем реальный компилятор
    let status = Command::new(rustc_path)
        .args(&args)
        .status()
        .expect("Не удалось запустить rustc");

    std::process::exit(status.code().unwrap_or(1));
}

Это весь скелет. Пять чётких шагов. Никакого разделения строк, никакого хрупкого индексирования, нулевая потеря данных.

Основные понятия

Протокол обёртки и разделитель -

Cargo вызывает обёртки, используя строгий формат:

<wrapper_binary> - <actual_rustc_path> <rustc_args...>

wrapc::fetch() автоматически:

  1. Отбрасывает первые три аргумента
  2. Сохраняет реальный путь к компилятору в info.rustc
  3. Разбирает оставшуюся часть как аргументы rustc

Краевой случай с -

Инструменты иногда передают - как имя входного файла, чтобы указать rustc читать из stdin. Поскольку протокол обёртки также использует - как разделитель, наивные парсеры здесь ломаются.

wrapc обрабатывает это контекстуально:

#![allow(unused)]
fn main() {
// Вызов: `my_wrapper - rustc -`
let info = wrapc::fetch().unwrap();
assert_eq!(info.rustc, Some("rustc".to_string()));
assert_eq!(info.inputs, vec![std::path::PathBuf::from("-")]);
}

Первый - — это разделитель протокола; второй правильно идентифицируется как входной файл.

Типобезопасный разбор флагов

Вместо возврата Vec<String>, wrapc разлагает сложные флаги на структурированные типы:

ФлагПоле для разбораТип
--emit=llvm-ir,objinfo.emitVec<EmitKind>
--extern crate=pathinfo.externsVec<Extern>
-L kind=pathinfo.libpathsVec<LibrarySearchPath>
-l kind:+mods=name:renameinfo.linksVec<LinkLib>

Это позволяет писать логику вроде:

#![allow(unused)]
fn main() {
use wrapc::{LibrarySearchPathKind, LinkLibKind};

for lib_path in &info.libpaths {
    if lib_path.kind == LibrarySearchPathKind::Native {
        println!("Путь для нативного поиска: {:?}", lib_path.path);
    }
}

for link in &info.links {
    if matches!(link.kind, Some(LinkLibKind::Static)) {
        println!("Статическая библиотека: {} (модификаторы: {:?})", link.name, link.modifiers);
    }
}
}

Никаких регулярных выражений. Никакого ручного разделения. Просто типизированные данные.

Безупречное сквозное восстановление

Обёртка никогда не должна нарушать сборку. Когда вы изменяете подмножество аргументов, всё остальное должно пройти точно так, как задумал Cargo.

wrapc гарантирует это через Info::to_args():

  • Сохраняет исходные пробелы и формы = или через пробел
  • Поддерживает порядок аргументов
  • Заново выводит неизвестные флаги из info.unknown без изменений
  • Обрабатывает краевые случаи, такие как значения в кавычках или встроенные пробелы

Вы изменяете то, что нужно; wrapc обрабатывает остальное.

Корректная деградация для nightly-флагов

Rust развивается. Ежедневно в nightly-компиляторах появляются новые флаги.

wrapc не притворяется, что знает их все. Вместо этого:

  1. Известные флаги -> разбираются в типизированные поля
  2. Неизвестные флаги -> сохраняются в info.unknown как сырые строки
  3. При to_args() -> все флаги выводятся заново в точности как были получены

Ваша обёртка не упадёт на новом nightly, и вы молча не потеряете экспериментальные флаги.

Основные моменты API

fetch() -> Result<Info, ParseError>

Точка входа. Читает std::env::args(), разбирает в соответствии с протоколом обёртки и возвращает строго типизированную структуру Info.

Структура Info (выбранные поля)

#![allow(unused)]
fn main() {
pub struct Info {
    // Метаданные протокола
    pub rustc: Option<String>,        // Путь к реальному rustc, если предоставлен

    // Общие флаги
    pub crate_name: Option<String>,
    pub edition: Option<String>,
    pub target: Option<String>,
    pub profile: Option<String>,      // "debug" или "release"

    // Флаги действий
    pub help: bool,
    pub version: bool,
    pub print: Option<String>,        // --print=<kind>

    // Компилируемые единицы
    pub inputs: Vec<PathBuf>,         // Исходные файлы
    pub emit: Vec<EmitKind>,          // --emit=...
    pub out_dir: Option<PathBuf>,

    // Управление зависимостями
    pub externs: Vec<Extern>,         // --extern crate=path
    pub libpaths: Vec<LibrarySearchPath>, // -L kind=path
    pub links: Vec<LinkLib>,          // -l kind:+mods=name:rename

    // Генерация кода и диагностика
    pub codegen_opts: Vec<String>,    // Значения флага -C
    pub cfg: Vec<String>,             // Значения --cfg
    pub features: Vec<String>,        // --cfg feature=...

    // Всё остальное для неизвестных/nightly-флагов
    pub unknown: Vec<String>,
}
}

Info::to_args(&self) -> Vec<String>

Восстанавливает исходный список аргументов без потери данных. Используйте это при передаче аргументов реальному rustc.

ParseError

Лёгкий тип ошибки, который указывает, почему разбор не удался (например, отсутствует значение, неправильный флаг). Большинство инструментов-обёрток могут безопасно использовать .expect() на fetch(), поскольку Cargo гарантирует правильно сформированные вызовы — но ошибка доступна, если она вам понадобится.

Продвинутый уровень: изменение контекста компиляции

Поскольку Info владеет своими данными, вы можете безопасно изменять поля перед восстановлением:

#![allow(unused)]
fn main() {
// Принудительно устанавливаем опцию codegen для всех крейтов
info.codegen_opts.push("target-cpu=native".to_string());

// Условно добавляем флаг cfg
if info.profile.as_deref() == Some("release") {
    info.cfg.push("feature=\"optimised\"".to_string());
}

// Заменяем путь внешней зависимости
for ext in &mut info.externs {
    if ext.name == "legacy_dep" {
        ext.path = PathBuf::from("/new/path/liblegacy_dep.rlib");
    }
}
}

Все изменения отражаются в выводе to_args().

Тестирование вашей обёртки

Вам не нужно публиковать или устанавливать глобально для тестирования. Используйте RUSTC_WRAPPER:

# Собираем вашу обёртку
cargo build --release

# Указываем Cargo на ваш бинарный файл
export RUSTC_WRAPPER="$(pwd)/target/release/my_wrapper"

# Запускаем любую команду cargo — ваша обёртка перехватит вызовы rustc
cargo build

Совет от бывалого: Всегда проверяйте info.help, info.version и info.print на раннем этапе в вашем main(). Если какой-либо из них установлен, немедленно передайте аргументы в rustc и выйдите. Это предотвращает вмешательство вашей обёртки во внутренние зонды компилятора Cargo.

Когда использовать wrapc

Идеален для:

  • Кэшей компиляции (инструменты вроде sccache)
  • Телеметрии или профилирования во время сборки
  • Обёрток статического анализа
  • Инжекторов флагов компоновщика или переменных окружения
  • Любого инструмента, реализующего RUSTC_WRAPPER

Не предназначен для:

  • Универсального разбора CLI (используйте clap, bpaf или argh)
  • Плагинов драйвера rustc (используйте API rustc_driver)
  • Разбора аргументов cargo (используйте cargo_metadata или специализированные парсеры)

wrapcli: Легко подделывайте идентичность командной строки

wrapcli — это библиотека Rust, которая оборачивает существующий инструмент командной строки и переписывает его вывод на лету, делая так, чтобы выглядело, будто вывод был создан другим инструментом.

Возможности

  • Потоковое переписывание вывода в реальном времени (строка за строкой)
  • Захват полного вывода для постобработки
  • Настраиваемые правила переписывания
  • Опциональное сохранение оригинальной информации о версии

Варианты использования

  • Создание брендированных вариантов CLI-инструментов
  • Маскировка внутренних имён инструментов в выводе, видимом пользователю
  • Добавление информации о версии без изменения нижележащего инструмента
  • Интеграция устаревших инструментов в современные рабочие процессы

Начало работы

Установка

Добавьте wrapcli в ваши зависимости:

cargo add wrapcli

Базовое использование

use wrapcli::{run_streaming, WrapConfig};

fn main() -> std::io::Result<()> {
    let cfg = WrapConfig {
        orig_name: "rustc".into(),
        fake_name: "dustc".into(),
        fake_ver: "2.0.0".into(),
        save_orig: true,
    };

    let args: Vec<String> = std::env::args().skip(1).collect();
    let status = run_streaming(&cfg, args)?;
    std::process::exit(status.code().unwrap_or(1));
}

Как это работает

Когда обёрнутый инструмент выводит строку, содержащую оригинальное имя, wrapcli перехватывает её и применяет правила переписывания:

  1. Первое вхождение оригинального имени и версии инструмента заменяется на поддельное имя и поддельную версию. Если save_orig равно true, оригинальная версия добавляется в скобках.
  2. Любые последующие вхождения оригинального имени в строках использования заменяются на поддельное имя.

Это обеспечивает согласованное маскирование вывода без нарушения функциональности инструмента.
