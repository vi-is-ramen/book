# Faces – унификация интерфейсов между крейтами

В любом достаточно сложном Rust-проекте вы в конце концов сталкиваетесь с одной и той же проблемой:
два крейта (или компонента), которые должны работать вместе, говорят на немного разных языках.
Один ожидает `Vec<u8>`, другой предоставляет `&[u8]`. Один использует собственный тип `Mutex`,
другой использует `std::sync::Mutex`. В итоге вы пишете связующий код – и очень много.

**Faces** — это минимальный крейт, совместимый с `no_std`, который предоставляет набор примитивных
типов и абстрактных трейтов, предназначенных для **бесконечного расширения**. Вместо того чтобы
навязывать конкретную реализацию, Faces предоставляет *лица* (faces) – общие интерфейсы, которые
вы можете реализовать для своих собственных типов. Таким образом, два иначе несовместимых API
могут взаимодействовать друг с другом через общую абстракцию.

## Философия

Faces — это не фреймворк. Он не диктует, как управлять памятью, обрабатывать конкурентность
или преобразовывать значения. Он делает следующее:

- Определяет **основные трейты**, такие как `Convertable<T>`, `AbsMutex<T>`,
`AbsPageFrameManager` и т.д.
- Предоставляет **тривиальные типы**, такие как `PageFrameNumber`, `PhysicalAddress`,
`VirtualAddress`, которые полезны в низкоуровневом коде (например, в ядре).
- Реэкспортирует популярные трейты (например, `serde::{Serialize, Deserialize}`) через
фичи (feature flags) для удобства.

Ключевая идея в том, что вы, автор крейта, можете реализовать эти трейты для своих собственных типов.
Тогда любой другой крейт, зависящий от Faces, сможет использовать ваши типы через тот же самый
хорошо известный интерфейс – без необходимости тянуть всё ваше дерево зависимостей.

## Основные трейты

### Трейты преобразования

Самая базовая потребность — преобразование одного типа в другой. Faces предоставляет
три пары безопасных и небезопасных трейтов преобразования:

```rust
pub trait Convertable<T> {
    fn to(self) -> T;
}

pub trait ConvertableRef<T> {
    fn to(&self) -> T;
}

pub trait ConvertableMut<T> {
    fn to(&mut self) -> T;
}
```

И их небезопасные аналоги: `UnsafeConvertable`, `UnsafeConvertableRef`,
`UnsafeConvertableMut`. Небезопасные преобразования полезны, когда вам нужно
переинтерпретировать память (например, превратить `VirtualAddress` в ссылку).

Пример: реализация безопасного преобразования из `MyId` в `u64`:

```rust
use faces::Convertable;

struct MyId(u32);

impl Convertable<u64> for MyId {
    fn to(self) -> u64 {
        self.0 as u64
    }
}

let id = MyId(42);
let val: u64 = faces::to(id); // или id.to()
```

Для удобства предоставляются вспомогательные функции `to`, `ref_to`, `mut_to`.

### Примитивы синхронизации

Faces определяет **абстрактные** блокировки и вспомогательные средства синхронизации.
Это не реализации – это контракты, которые может реализовать любая конкретная блокировка.

```rust
pub trait AbsMutex<T: ?Sized + Send, R: AbsRelaxStrategy> {
    type Guard<'a>: DerefMut<Target = T> + Send;
    fn lock(&self) -> Result<Self::Guard<'_>, LockError>;
    fn try_lock(&self) -> Result<Self::Guard<'_>, LockError>;
}
```

Вы можете реализовать `AbsMutex` для `std::sync::Mutex`, `spin::Mutex`, вашей собственной
спин-блокировки ядра и т.д. Параметр `R: AbsRelaxStrategy` позволяет указать, что означает
«расслабление» (например, `core::hint::spin_loop` или вызов `yield`). Тот же шаблон существует
для `AbsRwLock`, `AbsOnce` и `AbsLazy`.

Опциональные расширения с таймаутами (`AbsMutexTimeout`, `AbsRwLockTimeout`) предоставляют
вам попытки захвата блокировки с ограничением по времени.

### Примитивы управления памятью

Если вы работаете с физической памятью (например, в ядре ОС или гипервизоре),
вам часто нужны абстракции для страничных кадров и адресов.

- `PageFrameNumber`: простая обёртка вокруг `usize` с арифметическими, побитовыми трейтами
и трейтами форматирования. Преобразуется в `PhysicalAddress` и обратно (в предположении
страниц размером 4 КиБ).
- `PhysicalAddress` и `VirtualAddress`: обёртки-новотипы для адресов с `Display`
(шестнадцатеричное форматирование) и опциональной поддержкой `serde`.
- `AbsPageFrameManager`: трейт, который может реализовать любой менеджер физической памяти.
Он предоставляет методы для установки/сброса/проверки флагов на страничном кадре,
запроса допустимого диапазона и проверки присутствия.
- `AbsAddressTranslator`: преобразует виртуальные адреса в физические и обратно.

Эти возможности особенно полезны при написании платформонезависимого кода управления памятью.
Например, вы можете написать обобщённый аллокатор страниц, который работает с любым
`AbsPageFrameManager`.

## Фичи (Feature Flags)

Faces оставляет свои зависимости опциональными:

- **`std`** (включена по умолчанию): подключает стандартную библиотеку. Отключите её для
окружений `no_std`.
- **`serde`**: выводит реализации `Serialize` и `Deserialize` для `PageFrameNumber`,
`PhysicalAddress`, `VirtualAddress` и других будущих типов.
- **`log`**: реэкспортирует трейт `log::Log`.

В вашем `Cargo.toml`:

```toml
faces = { version = "0.1", default-features = false, features = ["serde"] }
```

## Расширение Faces

Поскольку Faces предоставляет только трейты, предполагается, что вы
**реализуете их для своих собственных типов**. В этом и заключается дизайн «бесконечного расширения»:
сам крейт никогда не разрастётся до включения всех возможных преобразований или типов блокировок.
Вместо этого вы – и сообщество – пишете реализации в своих собственных крейтах.

Например, если у вас есть собственный тип `Mutex`, добавьте это в ваш крейт:

```rust
use faces::{AbsMutex, AbsRelaxStrategy, LockError};
use core::ops::DerefMut;

struct MyMutex<T> { ... }

impl<T: Send, R: AbsRelaxStrategy> AbsMutex<T, R> for MyMutex<T> {
    type Guard<'a> = MyMutexGuard<'a, T>;
    fn lock(&self) -> Result<Self::Guard<'_>, LockError> { ... }
    fn try_lock(&self) -> Result<Self::Guard<'_>, LockError> { ... }
}
```

Теперь любой код, зависящий от Faces, может использовать `MyMutex` везде, где требуется `AbsMutex`.
То же самое относится к преобразованиям: реализуйте `Convertable<YourType>` для `TheirType`
и наоборот.

## Реальный пример: связывание двух крейтов

Предположим, у вас есть крейт A, который производит `CustomFrameId` (номер страничного кадра),
и крейт B, который ожидает `faces::PageFrameNumber`. Вместо того чтобы изменять какой-либо из крейтов,
вы пишете небольшую прослойку:

```rust
use faces::{Convertable, PageFrameNumber};

impl Convertable<PageFrameNumber> for CustomFrameId {
    fn to(self) -> PageFrameNumber {
        PageFrameNumber::new(self.raw())
    }
}

impl Convertable<CustomFrameId> for PageFrameNumber {
    fn to(self) -> CustomFrameId {
        CustomFrameId::from_raw(self.to())
    }
}
```

Теперь `faces::to::<PageFrameNumber>(custom_id)` работает, и два крейта могут взаимодействовать,
никогда не зная о внутренних типах друг друга.

## Куда двигаться дальше

Faces намеренно маленький – его истинная сила проистекает из экосистемы реализаций,
которые напишут другие. Ознакомьтесь с
[документацией API](https://docs.rs/faces/) для полного списка трейтов и типов.

Если у вас есть полезная абстракция, которая должна быть в Faces (например, трейт для
асинхронных блокировок или для счетчиков ссылок), смело открывайте issue или pull request
на [GitHub](https://github.com/vi-is-ramen/faces). Цель состоит в том, чтобы сохранить набор
трейтов минимальным, широко полезным и простым в реализации.

**Начните использовать Faces сегодня** – добавьте его в свой `Cargo.toml` и приступайте к реализации
этих «лиц». Ваше будущее «я» (и ваши пользователи) скажут вам спасибо за чистые, несвязанные интерфейсы.
